# CI pipeline — design

Date: 2026-11-17. Status: approach approved (option 1 below), owner rulings in; design awaiting final approval.

## Intent

Every test suite in this repo is run by hand today: Vitest, 66 pgTAP files, six race
scripts in `scripts/`, Playwright, lint and `next build`. The parts most likely to
regress (RLS, triggers, the registration/waitlist race safety that CLAUDE.md rule 1
exists for) are covered only by suites that need a running Supabase stack, so they are
the ones least likely to get run. CI runs all of them automatically and stops a red
build from reaching production.

Production today is deployed with `vercel --prod` from the owner's machine (Vercel lists
Ready production deploys; `main` holds only the Create Next App initial commit). As part
of this work production moves to the `main` branch, so that the CI gate actually sits in
front of what users get.

## Goals

- Every push to `dev` runs the full suite and reports pass/fail on the commit. Warn only.
- Every pull request into `main` runs the same suite, and the merge is blocked until it
  passes (branch protection, required checks).
- Merging into `main` is the only way production is deployed.
- A cheap failure (lint, types, unit) shows up in about 4 minutes, not after the stack boots.

## Non-goals

- Deploying from CI. Vercel's Git integration builds and deploys; CI only gates.
- Running anything against the hosted Supabase project, or pushing migrations to it.
  Migrations stay a manual owner step before each release (owner ruling, 2026-11-17; see
  Release checklist). No database secret goes into GitHub.
- Vercel preview deploys. Only `main` builds on Vercel (owner ruling, 2026-11-17): a preview
  would read the Preview env vars, which are missing or point at the hosted production
  database, so a preview could write real data. CI already tests `dev`.
- Testing the `send-email` edge function or Resend delivery (see Constraints).
- Google OAuth, or e2e coverage beyond what `tests/e2e/` already has.
- Preview-deploy smoke tests against the Vercel preview URL.

## Anti-goals

- A flaky gate. A check that fails at random gets ignored or turned off, which is worse
  than no check. The race scripts' thresholds (`ARRIVAL_SPREAD_THRESHOLD_MS`) must be
  tuned for a CI runner, not left at the dev-machine value, if they flake there.
- Any secret in the workflow. The repo is public (`api.github.com/repos/bagasfai/twogether`
  answers 200 without auth), so fork PRs run the workflow too. Everything CI needs comes
  from the local stack it boots.
- Tests that touch a non-local database. The e2e suite's local-only guard
  (`tests/e2e/support/local-guard.ts`) and the race scripts' schema guard stay as they are.

## Constraints

- **Public repo**: Actions minutes are unlimited and branch protection is free.
- **Supabase CLI** is a devDependency (`supabase ^2.117.0`, local 2.117.0), so `npx supabase`
  works after `npm ci`. No separate setup action.
- **Node**: local is 22.21.1. CI uses Node 22.
- **The `send-email` auth hook** (`supabase/config.toml` `[auth.hook.send_email]`) calls
  Resend and returns 401 on any error, so signup and password reset fail without a real
  `RESEND_API_KEY`. CI turns the hook off (rewrite `enabled = true` to `false` in that
  block before `supabase start`). Auth then uses its built-in mailer. The e2e suite never
  reads mail: it builds confirmation and recovery links with `auth.admin.generateLink`
  (`tests/e2e/support/admin.ts`). Cost: CI never exercises the hook.
- `supabase start` resolves `env(SEND_EMAIL_HOOK_SECRET)` from the config, so CI sets a
  throwaway value in that env var.
- **Ports** are non-default (API 54331, DB 54332). The race scripts read the DB URL from
  `supabase status -o env`, and the e2e guard reads the API port from `config.toml`, so
  neither needs changes.
- **E2E env**: `tests/e2e/support/env.ts` loads `.env.local` through `@next/env`. CI writes
  `.env.local` from `supabase status -o env` (API URL, anon key, service role key) plus
  `NEXT_PUBLIC_SITE_URL=http://127.0.0.1:3000`. Playwright starts `next dev` itself
  (`playwright.config.ts` `webServer`), with `RESEND_API_KEY` empty.
- The seed runs on `supabase start`. pgTAP and race tests are already scoped to their own
  fixtures (commit `0191843`).

## Approaches

1. **Two parallel jobs (chosen).** `checks` (no Supabase) and `db-and-e2e` (full stack),
   both required. Fast feedback on cheap failures, and one failure doesn't hide the
   other job's results. Costs about 3 extra minutes per run (two `npm ci`).
2. **One job, sequential.** Simplest file, fewest minutes. The first failure ends the run,
   so a lint error hides the database results, and feedback is always ~15 minutes.
3. **One job per suite, each with its own stack.** Fastest wall clock, but `supabase start`
   (2-4 minutes) runs three times. Rejected: not worth it for a solo repo.

## Design

One workflow file, `.github/workflows/ci.yml`.

**Triggers**: `push` to `dev`; `pull_request` targeting `main`. A `concurrency` group per
ref with `cancel-in-progress: true`, so a new push cancels the stale run for that branch.

**Job `checks`** (ubuntu-latest, Node 22, npm cache):
`npm ci` → `npm run lint` → `npx tsc --noEmit` → `npm run test:unit` → `npm run build`.
The build runs with dummy, well-formed Supabase env values (`NEXT_PUBLIC_SUPABASE_URL`
pointing at an unused `http://127.0.0.1:<port>`, placeholder keys) and no
`NEXT_PUBLIC_SITE_URL`, so `app/sitemap.ts` returns `[]` without querying. The builder
must confirm the build passes this way. If some page queries Supabase at build time and
fails, move `npm run build` into `db-and-e2e` after the stack is up, and say so.

**Job `db-and-e2e`** (ubuntu-latest, Node 22, npm cache):
1. `npm ci`.
2. Turn off the send-email hook in `supabase/config.toml` (CI working copy only), export a
   throwaway `SEND_EMAIL_HOOK_SECRET` (format `v1,whsec_<base64>`).
3. `npx supabase start`, excluding services nothing uses (Studio and others; the builder
   picks the list and checks that nothing the tests touch is excluded).
4. `npx supabase test db` (pgTAP).
5. The six scripts in `scripts/` (`test-concurrent-*.sh`, `test-public-community-stats.sh`).
   `psql` must be available on the runner.
6. Write `.env.local` from `supabase status -o env`, install the Playwright Chromium
   browser (cached by Playwright version), `npm run test:e2e`.
7. On failure, upload the Playwright report and traces (`trace: "retain-on-failure"` is
   already set) as an artifact.

Steps 4-6 run even if an earlier one fails (`if: !cancelled()` or equivalent), so one red
suite doesn't hide the others. The job still ends red.

**Required checks**: both job names, on `main`.

**Vercel builds only `main`**: add `"git": {"deploymentEnabled": ...}` to `vercel.json` so
`main` deploys and every other branch (including fork PR branches) does not. The builder
checks the exact syntax and how overlapping branch patterns resolve against the current
Vercel docs, and keeps the existing `crons` entry.

## Owner setup (manual, outside the repo, one time)

The builder writes these down as steps in the plan for the owner, in this order. CI must be
green on `dev` first.

1. **Before the first merge, bring the hosted schema up to date.** The first push to `main`
   is itself a production deploy, and the hosted project may be missing migrations from
   `20261026000001` onward. Run `npx supabase migration list` against the linked project,
   then `npx supabase db push`, and redeploy the `send-email` function. Also check that the
   Vercel Production env vars (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SITE_URL`, `CRON_SECRET`) hold hosted values.
   Production deploys already succeed, so they most likely do, but a Git build reads the
   values stored on Vercel, not the owner's local env.
2. Vercel → Project `twogether` → Settings → Git: confirm the GitHub repo is connected, and
   set Production Branch to `main`. Stop running `vercel --prod` by hand.
3. Fast-forward `main` to `dev` (`main` is an ancestor of `dev`): `git push origin dev:main`.
   This deploys production.
4. GitHub → Settings → Rules → new branch ruleset on `main`:
   - require a pull request, with 0 approvals (solo owner; nobody else can approve);
   - require the two CI checks to pass;
   - block force pushes and deletion;
   - allow only the "merge commit" merge method (design call, not an owner ruling: a squash or rebase merge
     puts commits on `main` that `dev` lacks, so every release would need a back-merge;
     merge commits leave `main` one merge commit ahead, which causes no conflict);
   - enforced on the owner too, with the owner on the bypass list (design call, not an owner ruling): bypass
     is a deliberate, logged action, kept for a hotfix when CI itself is broken.

## Release checklist (every release)

1. CI is green on the `dev` head.
2. If the release adds migrations: `npx supabase db push` to the hosted project, and check it
   applied. If it touches `supabase/functions/`, redeploy that function.
3. Open a `dev` → `main` pull request, wait for the required checks, merge with a merge commit.
4. Vercel builds and deploys `main`.

The release checklist goes in the README, next to the CI section.
