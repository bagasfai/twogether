# Photo Gallery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the photo gallery end to end: a "Start session" host action, automatic per-session albums, upload by checked-in participants, host/admin approval, and public gallery pages that show approved photos.

**Architecture:** Three migrations. State transitions (`start_session`, `review_gallery_photo`), the upload eligibility rule and the 20-pending cap live in Postgres (SECURITY DEFINER RPCs, one trigger, RLS, Storage policies). Server Actions are thin wrappers that map JB error codes and call `revalidatePath`. Public pages are ISR through the cookieless anon client; upload/review UI are client islands and `(app)` components.

**Tech Stack:** Next.js App Router (breaking-changes version, see Task 1), Supabase (Postgres, RLS, Storage), pgTAP, TypeScript strict, zod, shadcn/ui, next-intl (marketing only), Vitest.

**Spec:** `docs/superpowers/specs/2026-10-21-gallery-design.md`

## Global Constraints

- Design is locked to `design.md` + `tokens.css`: modern-minimal, Coral, Geist, ink-filled pill CTAs, coral as highlighter only. Use tokens only (`--color-*`, `--space-*`, `--text-*`, `--radius-card`, `--radius-pill`, `--radius-input`, `--dur-short`, `--ease-out`). No raw colour, px, ms or easing values. Introduce no new token.
- Upload cap: 20 `pending` photos per user per album. Upload window: `now() <= sessions.ends_at + interval '7 days'`. Bucket `gallery`: public, 5 MB, jpeg/png/webp. Path: `{gallery_id}/{uuid}.webp`. Resize: max 2000px long edge, webp quality 0.82.
- Reject and Delete are hard deletes with confirm-hold (about 600ms), no dialog, no undo.
- RPC pattern: `SECURITY DEFINER`, `set search_path = public, pg_temp`, `revoke ... from public, anon`, `grant ... to authenticated`, errors via `raise exception ... using errcode = 'JBxxx'`. Map off `error.code` only.
- Next free JB codes start at **JB012** (JB001–JB011 used). Allocation in Task 4.
- `(marketing)` pages use next-intl, keys in both `messages/en.json` and `messages/id.json` under a `gallery` namespace. `(app)` pages use plain English strings.
- After any migration run `npx supabase db reset` then `npx supabase test db`. Regenerate types once all three migrations exist (Task 9) with `npx supabase gen types typescript --local > types/supabase.ts`.
- No E2E tests. pgTAP + Vitest only. No reorder UI, no notifications, no orphan-file cleanup.
- Next.js APIs may differ from training data. Task 1 is a docs read; do it before any app code.

## Review Focus

Failure modes the spec implies but its test list does not name. Each has a test in the task shown.

- A reviewer approves while another rejects the same pending photo: the loser gets `JB016`, never a 500 or a double effect (Task 7).
- Host double-clicks "Start session" or a co-host starts it concurrently: second call gets `JB016`, exactly one album exists (Task 2).
- A session is deleted: its album survives with `session_id` null, only admins can review its pending photos, pending photos stay invisible to anon (Task 7).
- Uploader's profile is deleted (`uploaded_by` becomes null): the pending photo is visible to reviewers only and still reviewable (Task 7).
- User picks a HEIC, a non-image, a 0-byte or >5MB file: the client rejects it with a per-file error before any network call (Tasks 10, 13). An album opened by direct URL with zero approved photos renders an honest empty state, not an error (Task 12).
